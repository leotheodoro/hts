# 0026 · Sincronização app ↔ API

Data: 2026-10-28 · Status: aceita (#19). Concretiza a 0008.

## Decisão
- O app continua offline-first: toda escrita vai primeiro para o SQLite. O Postgres no Neon é a fonte da verdade e o backup.
- `POST /v1/sync/push` recebe as linhas que mudaram no aparelho, por tabela, como JSON com as colunas em snake_case (datas ISO 8601 com milissegundos, decimais como texto, jsonb como JSON). O servidor faz upsert por `id` com **última escrita vence**: a linha só é trocada se o `updated_at` recebido não for mais antigo.
- `GET /v1/sync/pull?since=` devolve as linhas que o servidor gravou depois do cursor. O cursor é `server_updated_at`, coluna só do Postgres, gravada pelo servidor em milissegundos: o relógio do aparelho não serve de cursor.
- O app guarda `last_push_at` (maior `updated_at` enviado) e `pull_cursor` em `local_sync_state` (tabelas `local_` não existem no Postgres). Cada sync envia as linhas com `updated_at >= last_push_at` e aplica as recebidas com a mesma regra de última escrita.
- Ordem das tabelas: pais antes de filhos (athlete, saga, arc, workout_template, block, exercise, prescribed_exercise, session, logged_set, logged_round, battle).
- A sync roda ao abrir o app, ao voltar para ele, ao finalizar um treino e pelo botão no Perfil. Sem URL ou token, o app fica só local. Timeout de 90 s, porque o Render gratuito leva cerca de 1 min para acordar.

## Consequências
- Um aparelho por enquanto: cada instalação cria o próprio atleta. Um segundo aparelho precisa adotar o atleta do servidor (ticket futuro, junto com contas).
- Linhas recebidas voltam no próximo push (eco idempotente); aceito pela simplicidade.
- Exclusões são lógicas (`deleted_at`) e viajam como qualquer outra mudança.
